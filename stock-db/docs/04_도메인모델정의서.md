# 04. 도메인 모델 정의서

> ERD 는 갑자기 그리는 그림이 아니라, **요구사항 문장에서 명사를 찾는 것**에서 시작한다.

## 1. 요구사항 문장 → 명사 추출

| 요구사항 문장 | 찾은 명사 |
|---|---|
| 종목은 **시장**(KOSPI, KOSDAQ)에 상장되어 있다 | 종목, 시장 |
| 종목은 하나의 **업종**에 속한다 (반도체, 자동차 ...) | 업종 |
| 종목은 매 거래일마다 **시세**(시가·고가·저가·종가·거래량)가 생긴다 | 일별 시세 |
| 종목은 해마다 **재무 정보**(매출·영업이익 ...)가 공시된다 | 연도별 재무 |
| 사용자는 종목에 대한 **메모**를 남긴다 | 메모 |

## 2. 엔티티 후보 → 최종 판단

| 후보 | 엔티티? | 판단 근거 |
|---|:---:|---|
| 종목 (Company) | O | 핵심 대상. 독립적으로 식별된다 (종목코드) |
| 시장 (Market) | O | 여러 종목이 공유하는 값. 문자열로 반복 저장하면 중복 |
| 업종 (Sector) | O | 위와 같음 |
| 일별 시세 (DailyPrice) | O | 종목 1 : N. 날짜마다 행이 쌓임 |
| 연도별 재무 (FinancialStatement) | O | 종목 1 : N. 연도마다 행이 쌓임 |
| 메모 (Note) | O | 사용자가 직접 만드는 데이터 (CRUD 실습) |
| 등락률 | X | 종가로 계산되는 **파생값** → 저장하지 않고 뷰로 계산 |
| PER / PBR | X (이번 범위 밖) | 발행주식수가 필요해 데이터가 더 필요 |

## 3. 엔티티별 속성

| 엔티티 | 식별자 | 주요 속성 |
|---|---|---|
| Market | market_id | name |
| Sector | sector_id | name |
| Company | company_id (대체키) / code (자연키, UNIQUE) | name, market_id, sector_id, created_at |
| DailyPrice | price_id / (company_id, trade_date) UNIQUE | open, high, low, close, volume |
| FinancialStatement | statement_id / (company_id, fiscal_year) UNIQUE | revenue, operating_profit, net_income, total_assets, total_liabilities, total_equity |
| Note | note_id | company_id, title, content, created_at |

## 4. 관계

```text
Market 1 ─── N Company        (한 시장에 여러 종목)
Sector 1 ─── N Company        (한 업종에 여러 종목, 업종은 비어 있을 수 있음)
Company 1 ─── N DailyPrice
Company 1 ─── N FinancialStatement
Company 1 ─── N Note
```

## 5. 업무 규칙 (DB 구조보다 먼저 정한 것)
1. 종목코드는 6자리이고 중복될 수 없다.
2. 한 종목의 같은 날짜 시세는 하나뿐이다.
3. 고가는 저가보다 작을 수 없고, 가격·거래량은 음수일 수 없다.
4. 종목을 삭제하면 그 종목의 시세·재무·메모도 함께 삭제된다.
5. 다른 종목이 쓰고 있는 시장/업종은 삭제할 수 없다.
